Action Graph: Bidirectional Planning
with Reversible Execution

Igor Steblii
Independent project · Swift, SwiftUI, SQLiteNovember 16, 2026

Abstract. A local system connects observed context to a measurable goal through competing hypotheses. A fixed execution pool explores candidate paths; a single FIFO grader evaluates completed tasks. Periodic decomposition review and a daily ledger revise priorities without rewriting history. We illustrate synthetic Unotone experiments toward $10M ARR. No current revenue or growth outcome is asserted.

1. Requirements and invariants

  1. Two frontiers. Recursively decompose goals; retain milestones at necessity confidence ≥ 0.50. Explorers and executors see local tasks, not private goals.
  2. Scheduling. A max heap refills N execution slots independently. One FIFO grader handles completions in order, projects goal alignment and records daily progress. Reserve bounded trials for weak candidates.
  3. Immutable outcomes. Require an undo plan before dispatch. Failure and compensation append new state nodes; verify restoration and preserve the failed outcome.
  4. Two node states. Only active or deactivated; reasons such as expired, error and dead_end are separate. Waiting/running belong to work records.
  5. Recovery. Bounded exponential retries precede deactivation/error. User allowance reactivates and queues next-run grading before one extra attempt.
  6. Persistent knowledge. Normalize all domain records and relations in SQLite. Version and vectorize nodes, edges, tags and resources. Validate strict plan/result templates, including undo.
  7. Four maintenance jobs. Clean stale heap entries; review deactivated paths when stuck; separately compare decomposition with active evidence to add or retire milestones. A fourth cron times out active jobs. All decisions append history.

2. Scientific foundations

Exploration versus exploitation. Bandits allocate trials between promising options and uncertain alternatives;[1] UCT extends this to sampled planning.[2] Our weak-candidate trials are budgeted heuristics, not guarantees of discovering rare opportunities.

Graph search and credit. Transpositions share information across equivalent states.[3] Keep action statistics separate: back up unique evidence along the executed lineage; replace an evaluation's contribution when revised. Similar text alone does not establish equivalence.

Compensation. Sagas amend partial execution through compensating actions.[4] Undo restores declared predicates in a new outcome. Actions without a credible restoration contract are ineligible; failed undo creates a separate recovery problem.

UCB reference: Q(e) + c√[ln(1 + Nsrc) / (1 + Ne)]

Limits. Business signals are delayed, coupled and nonstationary. These papers do not prove our system optimal. The demo uses a bounded priority heuristic, not a validated Monte Carlo business model. A connected route remains hypothetical until measured predicates verify the goal.

Restoration is a forward action: prior state → attempted action → observed failure → compensation → new, verified restoration state. The record of failure remains part of the graph.

3.1. Simulation model

A seeded event model samples durations and observations, maintains a binary heap and fills N execution slots. Completed tasks enter one FIFO; local grading and private goal projection run serially. Equivalent targets merge; intersecting paths share evidence.

P = 0.60Q + 0.20U + 0.10F + 0.10R

Q blends local grade and goal alignment; U rewards uncertainty, F discounts stale evidence and R preserves a recovery allowance. Every fifth allocation tests the lower-ranked tail. Four cron jobs maintain eligibility, decomposition and active-job deadlines. The grader appends daily task and node records.

3.2. Evaluation and limits

Compare forward-only, bidirectional and merge-enabled policies over matched seeds and budgets. Measure cost, time to verified goal, duplicate work, calibration error, false merges, unsafe actions and recovery outcomes.

No efficacy result is claimed. Scripted synthetic responses explain mechanics, not market behavior. Time is accelerated; the UI holds in-memory projections, not the native Swift/SQLite application. Real verification requires grounded metrics and independent evidence.

Action Graph / RequirementsSpecification 0.7 · Contracts 1.5 · 16 November 2026

System requirements

A local planning system that explores competing paths toward a measurable goal. A fixed execution pool acts independently; one FIFO grader evaluates results. Graph history remains immutable.

Observe → reason → candidate + plan → merge review → publish → execute → grade / project → backpropagate

1. Graph and planning

  1. 01Directed graph. Separate observed states, forward candidates, private goals, action edges and evidence. Append versions; preserve failed outcomes.
  2. 02Goal decomposition. Refine subgoals recursively within planning budgets. Snapshot a configurable necessity threshold in [0,1], default 0.5. Confidence is a belief, not proof.
  3. 03Three node states. candidate · active · deactivated. Keep reasons, job activity and goal verification separate. Private goal nodes are never execution work.
  4. 04Merge before publication. A separate agent reviews candidates. Similarity retrieves matches; structured state/action equivalence—including inputs, resource versions and effects—authorizes merging. The host publishes unmerged work atomically; uncertain candidates stay unpublished.
  5. 05Fixed execution capacity. Maintain N execution slots and a max-priority heap. Tasks finish independently; passive waits free slots. Reserve bounded trials for weak candidates and recovery.

2. Evaluation and verified success

  1. 06One grading queue. Grade completions serially in persisted completion order. Separate local quality from private goal alignment; unknown is null. Regrades and continuation decisions use the same FIFO.
  2. 07Graph-aware credit. Track reviewed edges/versions, evidence contexts and executed lineage. Duplicate reviews retain the higher valid score per context without extra visits or credit. Fresh evidence may lower scores; shared paths cannot multiply observations.
  3. 08Proof-based goals. Verify fresh, scoped predicates through an owner-approved sufficient rule. Connections and scores establish support only. Reject empty or circular rules.

Missing, stale, insufficient or conflicting evidence is unknown. Planning prerequisites prove a parent only through an approved sufficient rule.

3. Recovery and maintenance

  1. 09Predeclared undo. Every executable edge needs a baseline, restoration predicates, undo steps and reserved budget. Failure/restoration append nodes; retries wait for required restoration.
  2. 10Bounded recovery. Use persisted exponential backoff, jitter and model fallbacks before help. Manual approval permits one extra attempt after regrading. The grader decides resume, restart or remain blocked.
  3. 11Four independent cron jobs. Clean stale nodes; revive paths when stuck; review decomposition; detect execution deadlines/lease expiry. Fence stale workers, reconcile effects and preserve budgets across restart or sleep.

4. Data, models and native app

  1. 12Normalized persistence. Store nodes, edges, tags, resources, plans, runs, evaluations and audit links in SQLite with real keys and constraints. sqlite-vec indexes versioned content; scoped structured search remains available while embeddings are pending.
  2. 13Daily ledger. Include every completed attempt and each node’s state/progress, including pending grades, errors and unchanged nodes. Retain source references, completion/grade timestamps and append-only revisions.
  3. 14Editable contracts. Keep plan, result, daily-report, merge-review, local-grade, goal-projection and resume/restart templates as separate source files. Validate closed schemas, references, roles and evidence; snapshot template versions/hashes.
  4. 15Entity content limits. Every first-class entity has a title, description <300 and body <4000 characters. Normalize NFC and count Unicode scalars; reject oversize output. Large resources use attachments/chunks.
  5. 16Swift and SwiftUI. Use Swift actors/concurrency for the engine and a database actor for writes. User settings supply an OpenAI-compatible completion endpoint, execution/grader models and a fallback for each, plus a separate embedding API/model. Store credentials in Keychain.
  6. 17Minimal native workspace. Compact project menu and on-demand search. Keep goals/progress, running jobs, blocked work and user actions visible. Inspect nodes, edges, expected/observed weights, plans, undo and resources; offer Up next, Activity and Daily report views.

Implementation: prompts and inbox parsing

First-release approach. Extend the existing cloud inbox dispatcher and session-completion handler. One task requests one operation; a prompt specifies the required JSON result. The cloud validates the expected run’s final response and applies the selected review policy.

Reuse TaskSquad projects, agents, tasks/messages and resources. Graph tab setup collects name, start state, goal, agents, N, necessity threshold (default 0.5), review mode and advanced budgets. New graph CLI/submission infrastructure is deferred.

auto-accept or user review → normalized graph update

2. Add one small linkage table

graph_task_runs: graph/node/task references; operation; expected agent/session; template/config/input versions; parse status; response hash; acceptance timestamp; repair source.

Retain raw output/errors for troubleshooting. Accepted subgoals, plans and results become normalized domain records. Node lifecycle remains candidate / active / deactivated; parser status is separate.

3. Parse only the expected final result

  1. Match the run. Read final_text from the existing completion handler. Check linked task, authenticated agent and expected session.Ignore user/supervisor messages, tool output, intermediate replies and stale runs.
  2. Parse + validate. Allow whitespace or one enclosing JSON code fence; parse the complete document against the operation’s schema.Reject extra fields, invalid references, oversized content and out-of-range values. Never extract JSON from arbitrary prose.
  3. Repair format only. Preserve invalid output as parse_error. Use a bounded formatting-only inbox follow-up with a newly expected run.“Preserve the existing facts. Do not execute the task or repeat any actions.” No new execution attempt is granted.
  4. Apply the review policy. Auto-close still requires validation. Review mode holds the transition until approval of that exact result.Store results durably; duplicate callbacks/approvals cannot apply graph changes twice.

4. Deliver the shared parser first

Milestone 1: Graph creation → decomposition inbox task → parsed/approved response → visible subgoals. Test malformed JSON, wrong run, repair and both review modes.

Then reuse it: planning/merge → one reversible execution → single FIFO local-grade/projection chain. Add configured concurrency, four cloud crons, recovery and daily logs after the round trip works.

Acceptance gates remain. Candidate merge review, predeclared undo, evidence-based AND/OR verification and duplicate-safe lineage credit are enforced by cloud code. A parse error is not an execution failure. Grading/repair preserves the original completion-order position.
